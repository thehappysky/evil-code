## 第 2 步：入口与主循环

### 2.1 启动流程

入口文件：`crates/codegen/xai-grok-pager-bin/src/main.rs`，函数 `fn main()` → `run_agent_command()`。

启动流程 6 个阶段：

**阶段 1：早期检查**
- `check_previous_crash()` —— 检测上次会话是否崩溃，如有则符号化 backtrace 并展示报告
- `enforce_minimum_version_or_exit()` —— 低于最低版本则强制升级后退出
- 可选 auto-update 后台检查

**阶段 2：CLI 参数解析**
- 解析子命令：`grok`（TUI）、`grok -p`（Headless）、`grok dashboard`、`grok agent`（Leader/Stdio）
- 解析选项：`--yolo`、`--model`、`--cwd`、`--sandbox`、`--json-schema` 等

**阶段 3：配置加载**
- 加载 `~/.grok/config.toml` 用户配置
- 加载远程设置（remote settings）
- 解析 AgentConfig：endpoints（API URL）、auth、模型目录、feature flags

**阶段 4：运行时初始化**
- 进程级 tokio runtime：`tokio::runtime::Builder::new_multi_thread().enable_all().build()`
- 安装崩溃 handler（SIGBUS/SIGSEGV + Windows SEH）
- 初始化 AuthManager（OAuth2/OIDC/API Key 认证）
- 初始化 ModelsManager（模型目录 + 端点解析）

**阶段 5：分发到运行模式**

| 模式 | 入口函数 | 触发条件 |
|:---|:---|:---|
| 交互式 TUI | `run_agent_command()` → ratatui | `grok` 无参数 |
| Headless | `run_headless()` | `grok -p "prompt"` |
| Leader 模式 | `run_leader()` | `grok agent --leader` |
| Stdio Agent | `run_stdio_agent()` | `grok agent stdio`（IDE ACP 集成） |
| Dashboard | TUI 进入 dashboard 视图 | `grok dashboard` |

**阶段 6：TUI 启动**（交互式模式）
- `MvpAgent` 通过 `LocalSet` 创建
- `run_agent_server()` 启动 ACP 服务器
- 进入 ratatui 事件循环

### 2.2 Agent 主循环（三层循环结构）

#### 外层：MvpAgent 的 RPC 循环

运行在 `LocalSet` 单线程上，通过 ACP 协议接收消息：

```
接收 ACP 消息 → 分发：
  session/new    → 创建 SessionActor，spawn 到独立 OS 线程
  session/load   → 从 JSONL 恢复 SessionActor
  session/prompt → prompt_intake_lock 序列化 → SessionCommand::Prompt 入队
  session/cancel → CancellationToken 级联取消
```

#### 中层：SessionActor 的命令处理循环

每个 session 运行在**独立 OS 线程（8MB 栈）+ 单线程 tokio runtime + LocalSet** 上。`run_session()` 函数（`run_loop.rs`）使用 `tokio::select!`：

```
loop {
    tokio::select! {
        cmd = cmd_rx.recv() →
          Prompt → handle_prompt()
          Cancel → 取消当前 turn
          SetModel → 更新 sampling config + 清除缓存
          Shutdown → 退出
        event = chat_state_event_rx.recv() → 处理 ChatState 事件
        event = event_rx.recv() → 处理内部 SessionEvent
    }
}
```

#### 内层：单轮推理循环（Turn Loop）

`handle_prompt()` → `process_conversation_turn()` 是核心的**思考→行动→观察**循环：

```
1. prepare_tool_definitions_timed()
   → 收集所有可用工具定义（内置 + MCP + Plugin）
   → 等待 MCP 初始化（Blocking 策略时阻塞）

2. build_conversation_request()
   → ChatStateActor 获取完整对话历史 (Vec<ConversationItem>)
   → 注入 system reminders (TodoGate, date, plan mode...)
   → 注入 tool definitions
   → 估算 token → 超阈值则触发 auto-compaction

3. loop (最多 max_turns 次):
   a. sampler.sample(request) → 流式 LLM 调用
      → text_delta → 实时推送 TUI
      → tool_call_delta → 累积参数
      → thinking_delta → 推送思考块

   b. 响应完成：
      EndTurn → 退出循环
      ToolCalls → 进入步骤 4
      ContentFilter → refusal 处理

   c. 工具执行:
      → 解析 tool_calls → 验证参数 (serde_path_to_error)
      → 权限决策 (7层管道)
      → FuturesUnordered 并发执行
      → ToolResult → ChatStateActor
      → 检查 max_turns / doom_loop

4. turn_end → 记录 token → 持久化 → Goal 验证 → trace 上传
```

**循环退出条件**：
- `stop_reason == EndTurn`（模型决定结束）
- `tool_turn_count >= max_turns`（达上限）
- Ctrl+C（CancellationToken 级联取消）
- ContentFilter（安全拦截）
- 推理错误（auth/network failure）

**异步关键 await 点**：
- `sampler.sample(request)`：等待 LLM 流式响应（SSE）
- `FuturesUnordered`：收集并发工具执行结果
- `chat_state_handle.push_tool_result()`：对话状态更新
- `persist_chat_history()`：JSONL 持久化

## 第 3 步：核心数据结构

### 3.1 Agent 状态结构体

#### MvpAgent（`agent/mvp_agent/mod.rs:594`）

整个 Agent 进程的顶级管理器。使用 `RefCell`/`Rc`（`!Send`，运行在 LocalSet 单线程上），避免数百个并发 ACP handler 的同步开销。

关键字段：
- `sessions: RefCell<HashMap<SessionId, SessionHandle>>` — 所有活跃 session
- `activity: AgentActivity` — Send+Sync 的 session 活动摘要（供 leader 读取）
- `prompt_intake_locks: RefCell<HashMap<SessionId, Rc<Mutex<()>>>>` — per-session prompt 入队顺序锁
- `cfg: RefCell<AgentConfig>` — Agent 全局配置
- `auth_manager: Arc<AuthManager>` — 认证管理器（token 刷新、OAuth 流程）
- `models_manager: ModelsManager` — 模型目录 + 端点解析
- `gateway: GatewaySender` — ACP 协议消息发送通道

#### SessionActor（`session/acp_session.rs:564`）

单个会话的完整状态。每个 session 独占一个 OS 线程 + 独立 tokio runtime。

关键字段：
- `chat_state_handle: ChatStateHandle` — 对话状态 Actor handle（命令+查询）
- `permissions: PermissionHandle` — 7 层权限决策管道
- `tool_context: ToolContext` — 工具执行上下文
- `mcp_state: Arc<TokioMutex<McpState>>` — MCP 服务器状态
- `pending_interjections: InterjectionBuffer` — 用户 mid-turn 消息缓冲
- `compaction: CompactionConfig` — Compaction 配置和运行时状态
- `memory: SessionMemory` — Memory 子系统
- `max_turns: Option<usize>` — 最大工具调用轮数
- `doom_loop_recovery: Option<DoomLoopRecoveryPolicy>` — Doom loop 检测策略
- `file_state_tracker: Arc<FileStateTracker>` — 文件状态追踪（用于 rewind）
- `max_retries: u32` — 最大重试次数

#### ChatStateActor（`chat-state/src/actor/mod.rs:30`）

Actor 模式的对话状态管理器。**独占 `&mut self`，零锁开销**。

关键字段：
- `state: ChatState` — 内部状态
- `persistence: Box<dyn ChatPersistence>` — 持久化策略
- `cmd_rx: UnboundedReceiver<ChatStateCommand>` — 命令接收端
- `event_tx: UnboundedSender<ChatStateEvent>` — 事件发送端
- `cancellation_token: CancellationToken` — 取消信号

**ChatState 子结构**（`chat-state/src/types.rs`）：
- `conversation: Vec<ConversationItem>` — 完整对话历史
- `sampling_config: SamplingConfig` — 当前采样配置
- `prompt_index: usize` — 当前 prompt 序号（递增）
- `total_tokens: u64` — 累计 token 使用量
- `agent_edited_paths: BTreeSet<String>` — Agent 编辑过的文件路径
- `prompt_texts: Vec<String>` — 历史 prompt 文本（rewind 预览用）

### 3.2 消息结构体

#### ConversationItem（`sampling-types/src/conversation.rs:28`）

统一内部对话表示，**tagged enum**（`#[serde(tag = "type")]` 自描述序列化）：

```
ConversationItem:
  System(SystemItem)          ← 系统指令（仅 conversation[0]）
  User(UserItem)              ← 用户输入（含 synthetic system-reminder）
  Assistant(AssistantItem)    ← 模型回复（text + tool_calls[]）
  ToolResult(ToolResultItem)  ← 工具执行结果
  BackendToolCall(...)        ← 后端已执行工具（web_search 等）
  Reasoning(...)              ← Responses API 推理块
```

**ToolCall 子结构**（位于 AssistantItem 内）：
- `id: String` — 工具调用唯一 ID
- `name: String` — 工具名称（如 "read_file"、"grep"、"server__tool"）
- `arguments: String` — JSON 字符串（模型输出的原始参数）

**ToolResult 子结构**：
- `tool_call_id: String` — 对应 ToolCall 的 ID
- `content: String` — 工具执行结果文本（可能被截断）
- `is_error: bool` — 是否为错误结果

### 3.3 消息历史的存储与传递

**磁盘存储**（JSONL，非 SQLite）：

```
~/.grok/sessions/{url_encoded(cwd)}/{session_id}/
├── chat_history.jsonl   ← 每行一个 ConversationItem JSON
├── updates.jsonl        ← 每行一个 SessionUpdateEnvelope JSON
├── summary.json         ← 会话元数据
└── ...
```

**内存传递**（Actor 模式，非 `Arc<Mutex<Vec>>`）：

- **写入路径**：SessionActor → `ChatStateHandle::push_user_message()`（异步命令，mpsc channel）→ `ChatStateActor::push_user_message()`（独占 `&mut self`）→ `state.conversation.push()` → `persistence.replace_history()`（写 JSONL）

- **读取路径**：SessionActor → `ChatStateHandle::build_request()`（异步查询，oneshot 回复）→ ChatStateActor 遍历 conversation → 转换为 API 格式 → 返回

**为什么用 Actor 而非 `Arc<Mutex<Vec>>`？**

| 对比维度 | Arc+Mutex | Actor 模式 |
|:---|:---|:---|
| 锁开销 | 每次读写竞争 | 零（&mut self 独占） |
| 异步边界 | 不适合持有锁跨 await | 天然适配（命令队列） |
| 原子操作 | 需要外部协调 | Actor 内一次性完成 |
| 崩溃恢复 | 中毒风险 | 自动修复 Dangling Tool Calls |

## 第 4 步：工具系统

### 4.1 工具定义方式

工具使用 **Trait + 类型注册** 模式，不是 enum 或宏展开。

每个工具实现两个核心 trait：
- `xai_tool_runtime::Tool`：定义 `id()`、`run()`、`execute()` 核心行为
- `ToolMetadata`（xai-grok-tools 内）：定义 `kind()`（ToolKind 枚举）、`description_template()`、`tool_namespace()`、`requires_expr()` 等元数据

ToolKind 枚举决定了工具在模板渲染时的分类标识（`Read`/`Bash`/`Grep`/`Edit`/`Search`/`Task`/...），用于 `${{ tools.by_kind.read }}` 模板变量解析。

注册约束（类型安全编译期保证）：
```
T: Tool + ToolMetadata + Debug + Default + Send + Sync + 'static
T::Args: DeserializeOwned + JsonSchema + Into<ToolInput>
T::Output: Serialize + DeserializeOwned + Into<ToolOutput>
```

### 4.2 工具注册表

位于 `xai-grok-tools/src/registry/types.rs`。

**构建流程**：

```
Phase 1: 编译时注册
  ToolRegistryBuilder::new()
    → register::<BashTool>()
    → register::<ReadFileTool>()
    → ... 50+ 工具
    → 应用 ToolPacks（register_tool_pack() 外部注册）

Phase 2: 运行时 finalize
  ToolRegistryBuilder::finalize(config, ctx)
    → 验证 ToolServerConfig
    → 构建 TemplateRenderer（ToolKind → client name）
    → 注入运行时资源（Terminal, FS, Cwd, Skills...）
    → 按 config.tools 筛选激活
    → 注册到 LocalRegistry（进程内调度中心）
    → 激活条件满足的 Reminder
    → 产出 FinalizedToolset（Arc 共享，不可变）
```

**FinalizedToolset 内部结构**：

| 字段 | 类型 | 用途 |
|:---|:---|:---|
| `tools` | `parking_lot::RwLock<Vec<FinalizedTool>>` | 工具列表（读多写少） |
| `resources` | `SharedResources` | 运行时状态（TodoState, Terminal...） |
| `local_registry` | `LocalRegistry` | 进程内工具调度中心 |
| `renderer` | `Arc<TemplateRenderer>` | Lock-free 模板渲染 |
| `reminders` | `Vec<Box<dyn Reminder>>` | 跨工具提醒器（Skill 发现等） |

**FinalizedTool 单条目**：包含 `client_name`、`input_schema`（JSON Schema）、`output_converter`、`parse_input`（JSON→ToolInput）、`reverse_params`（client→规范名映射）等字段。

### 4.3 工具调用全链路

```
1. prepare_tool_call() -- 查找 + 参数解析
   → 在 FinalizedToolset.tools 中按 client_name 查找
   → reverse-remap 参数名（client-facing → 规范名）
   → try_parse: serde_path_to_error 反序列化
   → 失败 → handle_tool_parse_error() → 错误注入回对话
   → 产出 PreparedToolCall

2. 权限决策 -- 7 层管道
   YOLO → SafeCmd → PersistedGrant → SessionGrant → Allow/Deny → AutoClassifier → Ask

3. 并发执行 -- execute_tool_calls()
   → FuturesUnordered 收集所有 dispatch_futures
   → 同文件编辑：tokio::sync::Mutex 按 file_path 粒度串行化
   → 可中断等待工具：tokio::select! { tool_result, interjection }
   → 结果通过 (idx, result) 元组保序收集

4. 结果处理
   → output_converter: JSON → ToolOutput
   → 收集跨工具 Reminder 文本
   → 截断过长结果（truncate_with_preview，保留 footer 提示）
   → ConversationItem::ToolResult → ChatStateActor
```

**工具结果回注上下文的机制**：工具结果作为 `ConversationItem::ToolResult` push 到对话历史。下一轮 `build_conversation_request()` 时自动包含。模型在下一轮推理中看到结果，做出下一步决策。

## 第 5 步：模型交互层

### 5.1 使用的 Rust SDK

使用 **async-openai** crate（OpenAI 兼容协议），不是 Anthropic 专用 SDK。

`xai-grok-sampler` crate 封装了 `async_openai::Client`，提供：
- Chat Completions API（`/v1/chat/completions`，line-by-line SSE）
- Responses API（`/v1/responses`，event-stream SSE）
- 统一 `ConversationItem` 中间表示，可无损转换为两种 API 格式

支持后端：xAI Grok 系列模型、BYOK（自定义 API key + endpoint）、Ollama 本地模型、任意 OpenAI 兼容端点。

### 5.2 构造请求时传入的参数

`SamplingConfig` 在 `build_conversation_request()` 时构造：

| 参数 | 来源 | 说明 |
|:---|:---|:---|
| `model` | session 配置 / 用户 `/model` | 模型 ID |
| `temperature` | config / 远程设置 / 默认值 | 采样温度 |
| `top_p` | 同上 | 核采样 |
| `max_completion_tokens` | 模型定义 / config | 最大输出 token |
| `tools` | `prepare_tool_definitions_timed()` 输出 | **每轮动态刷新** |
| `tool_choice` | 条件设置 | Structured Output 时设 `required` |
| `json_schema` | 用户 `--json-schema` flag | 原生 structured output |
| `reasoning_effort` | 用户 `/effort` 命令 | thinking token 预算 |
| `stream` | `true`（始终） | SSE 流式响应 |

**tools 数组每轮动态刷新**（非缓存）：
- 内置工具（从 FinalizedToolset.tool_definitions()）
- MCP 工具（动态发现，可能有 server 重启/新增）
- Plugin 工具
- Plan Mode 过滤（Active 时只暴露 plan file 相关）
- StructuredOutput 合成工具（条件性注入）
- Fork session 父级 tool schema override

### 5.3 响应解析：文本 vs 工具调用

```
SSE chunk stream
  → eventsource_stream::Eventsource 解析
  → async_stream::stream! 变换
  → SamplingEvent 枚举:
      StreamStarted
      ContentDelta(text)           ← 文本回答
      ContentDeltaEnd
      ToolCallDelta{id,name,args}  ← 工具调用（增量累积）
      ToolCallDone
      ReasoningDelta(text)         ← 思考块
      Completed{usage,stop_reason}
      Failed{error}
```

区分逻辑（`process_conversation_turn()` 中）：
- 遍历 `response.items`：
  - `Assistant(item)` + `item.content` 存在 → 文本回答
  - `Assistant(item)` + `item.tool_calls` 非空 → 工具调用请求
  - `Reasoning` → 思考块
  - `BackendToolCall` → 后端已执行工具（无需本地执行）

Structured Output 额外处理：
- 检测 `StructuredOutput` 工具调用 → 验证是否单独出现
- `validate_structured_output(validator, args)` → jsonschema 校验
- 失败 → 错误注入 + 重试（最多 3 次）
- 成功 → 验证后 JSON 作为最终答案

## 第 6 步：提示词系统

### 6.1 System Prompt 的生成方式

System Prompt 是**模板文件 + 动态构建器 + 运行时渲染** 的组合，不是硬编码字符串。

**模板层**（`xai-grok-agent/src/prompt/template.rs`）：
- 三个 XOR 混淆的模板（编译时 `include_str!` 嵌入）：
  - `prompt.md`：主 Agent 完整 System Prompt
  - `subagent_prompt.md`：Subagent 精简版（约 3700 chars）

## 本项目最特殊的两个设计点

### 设计点 1：三层运行时隔离（进程 multi-thread × Agent LocalSet × Session 专用 OS 线程）

这不是简单的"用 tokio 异步"。Grok Build 将运行时划分了三个物理隔离的层次：

- **进程级**：`new_multi_thread` work-stealing 线程池。处理所有网络 I/O（HTTP/WebSocket）、TUI 渲染帧、Leader 协调。所有需要 `Send + Sync` 的组件在此层运行。

- **Agent 级**：`LocalSet` 在当前线程单线程执行。`MvpAgent` 管理数百个并发 ACP 连接，但因为所有 handler 在同一线程上 `spawn_local`，可以使用 `RefCell`/`Rc` 而非 `Arc<Mutex>`。这消除了 ACP handler 之间的所有锁竞争。

- **Session 级**：每个 Session 获得**独立的 8MB 栈 OS 线程 + 独立的单线程 tokio runtime**。Session 内的 `SessionActor` 所有字段都是 `!Send` 的，不需要任何同步原语。一个 session 的 panic 或死循环完全不影响其他 session。Session 之间通过 `SessionHandle`（channel-based）通信，零共享内存。

**为什么这样设计？** 因为 Agent 系统的并发模型天然是"每个会话独立、内部串行"的。用一个大锁保护全局状态是反模式——它把可以并行的会话串行化了。用细粒度锁又会导致死锁风险。三层隔离让"该并行的并行（跨 session），该串行的串行（session 内）"，各得其所。

### 设计点 2：Actor 模式的对话状态管理——ChatStateActor 独占 &mut self

对话状态是 Agent 系统中竞争最激烈的数据——模型推理、工具执行、compaction、持久化都需同时读写它。

传统的 `Arc<Mutex<ChatState>>` 方案有三大问题：
1. **锁竞争**：推理完成后要 push assistant message + tool results，compaction 要替换整个 history，持久化要 snapshot——它们互相阻塞
2. **跨 await 不安全**：tokio 的 Mutex 虽然可以跨 await 持有，但增加死锁风险
3. **无法保证原子性**：compaction 的"生成摘要→替换历史"是两个操作，中间状态可能被读到

Grok Build 的方案是将 ChatState 的所有权完全交给 `ChatStateActor`——一个运行在独立 tokio task 中的 Actor。外部只能通过 `ChatStateHandle`（持有 `mpsc::UnboundedSender`）发送命令，Actor 在自己的 `&mut self` 上串行处理。读取操作通过 `oneshot::Sender` 回复。

带来的收益：
- **零锁开销**：所有 mutation 都是独占 `&mut self`，编译器保证无数据竞争
- **崩溃自修复**：`ensure_conversation_integrity()` 在每次写边界自动检测并修复 Dangling Tool Calls（Ctrl+C 取消、进程崩溃、tokio task abort 遗留的未配对 tool call），包括去重重复 ToolResult
- **Compaction 原子性**：整个"生成摘要 → 替换历史 → 注入 post-compaction reminder"流程在 Actor 内一次性完成，外部永远看不到中间状态
- **测试极其简单**：Actor 是纯状态机，不依赖异步 I/O，所有逻辑可完全同步测试
- **优先级控制**：`tokio::select! { biased; cancellation, cmd }` 保证取消信号优先于命令处理
